# A关停点：下一步内核选择

2026-10-28，待用户决定；未下载、安装或集成新组件。依据[实测](report.md)，这次最小WebCodecs实现未达到光标标准，不等于证明所有浏览器实现都不可能达标。

## 已知与未知

真实Eagle中，同源原生video光标P95约6～7ms，新硬件偏好路径约68ms；新路径输入同步处理最大约0.2ms，问题发生在随后帧调度/提交等待。改为隐藏画面和限2个解码包均未解除。尚未有浏览器GPU进程跟踪证明唯一根因，不能宣称显卡坏、驱动坏或某API必然有缺陷。原片远跳约1.2秒是本样本测量，不是任意素材上限。

## 可选路线

| 路线 | 优点 | 代价与尚未证明部分 |
| --- | --- | --- |
| 原生HTML video作为唯一显示核心 | 已测光标较快；不用新依赖；普通播放/音频由宿主管理 | 不能可靠强制/确认GPU解码；解码帧缓存和准确反向逐帧可控性不足。会收缩已批准能力，不能擅自交付为等价方案 |
| libmpv原生内核，先隔离验证（建议） | 成熟播放/音频/寻帧核心；Windows可选D3D11VA或NVDEC，查询实际状态；可把前台调度移出Eagle渲染进程 | 增加原生组件、桥接与版本维护；绘制/标注叠加、窗口焦点和关闭回收必须重新验证；不保证本机一定达标 |
| 自写libavcodec/Direct3D内核 | 帧身份、内存及GPU路径控制最多 | 自己维护音频同步、色彩、寻帧、取消与设备丢失；工程风险最高，不建议当前优先 |

## 建议批准的下一小步

仅做libmpv隔离技术样机，不直接替换播放器。先选择来源/许可/校验明确的Windows x64构建，核对清单与实际体积再加载；建议新增组件磁盘上限200MiB，这只是拟定预算，不是已经测得的包体。不能满足上限或许可条件就停止，不能悄悄扩展。现有测试输出仍受E44的2GiB/单轮10分钟限制。

工作包括三块：原生播放与消息桥接；准确源帧/原片与完整代理同帧切换；标注叠加和窗口生命周期验证。不能把启动一个mpv窗口当完成整合，更不能通过CPU逐帧读回像素掩盖传输开销。首先复用同视频/同轨迹，与Eagle原生video比较；过光标/准确帧/关闭关后才加入后台整片编码。

部署倾向独立小宿主＋本地进程通信，减少绑定Eagle内置Node ABI；但原生视频窗口不能直接假定被HTML标注正确覆盖。需要Render API或经过验证的共享绘制/叠加方案，保持现有UI和数据边界。额外组件随应用私有目录发布，不修改系统或Eagle安装目录。

## 公开依据（2026-10-28核实）

- [mpv官方硬件解码选项](https://mpv.io/manual/stable/#options-hwdec)：D3D11VA/NVDEC及copy路径有明确差别，copy会回系统RAM；不等于零拷贝自动成立。
- [官方libmpv嵌入说明](https://github.com/mpv-player/mpv-examples/blob/master/libmpv/README.md)：Render API需要原生绘制上下文；简单窗口嵌入与自定义叠加能力不同。这是集成成本，不是换一个JS库。
- [mpv许可说明](https://github.com/mpv-player/mpv/blob/master/Copyright)：默认GPL；符合条件的构建可用LGPL，但配置开关本身不足以证明整包许可，链接依赖也要核对。当前项目许可证尚未定，不提前承诺可按任意许可分发。

尚未取得具体构建，因此实际包体、内存、速度和维护版本均待核实。此处不虚报节省比例或必达性能。
