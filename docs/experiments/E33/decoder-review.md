# E-33 长视频解码方向与体验验收草案

2026-10-25。回应用户要求：解释常驻解码器、磁盘代理和有界RAM；核对独显加速条件、代理空间与生成时间；保留JPEG作为可选路径；制定自动与人工验收。当前仅完成只读可行性调查与方案登记，没有实现或启用新后端，没有生成新媒体。

## 当前决定与边界

用户目标是长片尽量接近短片拖动，允许适量降低预览画质，必须明确无法达到的落差。JPEG路径先保留，拟与新后端共存并在设置切换；这是用户提出的方向，具体编码、默认模式和切换时机尚未定案。常驻解码、逐步建立磁盘代理、RAM前后窗口是候选组合，不是已验证架构。新后端若采用原生库，需要单独完成Eagle接入、依赖发行、源帧对应、颜色、音频与生命周期验证；不能仅凭FFmpeg支持编码就宣布可行交付。

## 大白话解释

常驻解码器相当于一直在岗的翻译员：打开文件与解码上下文后持续复用，不为每个小段重新启动工具。它不等于整片进RAM，也不等于强制占用独显。相隔很远的跳转仍可能需要重设读取位置。

代理相当于给厚重原片制作专门供翻阅的副本；可减分辨率、改压缩方式，也可保持分辨率。帧内代理让每张画面独立，不依赖从前一个关键帧连续算到目标。JPEG同样每帧独立；装入一个视频容器不必然比JPEG快，收益取决于常驻解码、I/O组织和渲染数据传递。

磁盘是仓库，RAM是桌面。仓库存整片压缩代理，桌面只摊开正在看的前后一些画面。后台可边播边制作后续仓库内容；每个已完成分段单独提交及索引，不假设未结束普通MOV的尾部索引已经可读。

## 当前机器只读核对

Win32_VideoController报告NVIDIA GeForce RTX 3060 Laptop GPU与Intel Iris Xe。Eagle现有FFmpeg列出cuda/d3d11va/qsv等接口，以及prores_ks、dnxhd、h264_nvenc、h264_qsv编码器。此为能力清单，不证明驱动可实际启动，也未测吞吐。NVDEC按GPU代际/编码/位深支持H.264、HEVC等，不包含ProRes；本机ProRes CPU编码/解码不能被描述成3060的NVDEC/NVENC加速。核显也可参与支持格式的硬件编解码。GPU回传CPU再转Canvas会增加开销，须盘点渲染路径。

## 代理容量预算

以下ProRes Proxy是说明代价的候选，不是最终选型。按Apple目标码率换算十进制MB/GB，内容为可变码率；音频/容器/索引/临时文件另计。

| 预览 | 约30fps，每分钟 | 约60fps，每分钟 | 60fps、10分钟 |
| --- | --- | --- | --- |
| 1280×720 | 173MB | 338MB | 3.38GB |
| 1920×1080 | 338MB | 683MB | 6.83GB |
| 2560×1440 | 约600MB | 约1.21GB | 约12.1GB |

720p与1080p来自Apple表的23/45/91Mbps；1440p按1080p像素比例估计，没有对应官方实测。现有5GiB预算在60fps下约容纳720p 15.9分钟、1080p 7.9分钟、1440p 4.4分钟，实际更少。不静默提高预算；两种模式的代理总额共用预算，不能各占5GiB，也不能默认保留双份整片。切换需关闭/取消旧任务并复用独立缓存身份，永久标注继续绑定原素材。

解码后的RGBA容量由分辨率×4字节×帧数确定，与代理压缩率无关。一分钟60fps：720p 12.36GiB、1080p 27.81GiB、1440p 49.44GiB。因此必须按RAM额度滚动保留；YUV/GPU优化可减小特定驻留表示，但不能把全部显存/系统副本忽略。

生成时间不是文件大小除以SSD速度。整条链受源解码、缩放/颜色、代理编码、写盘、前台争用中最慢环节限制。按净转码速度0.5×/1×/2×/4×，生成一分钟分别120/60/30/15秒。处理2秒启动窗口，2×时纯处理约1秒，另加源核验/索引/启动和音画准备。上一轮JPEG分段的23～28秒/分钟外推及按像素量的1080/1440估计不能直接用于新代理。此机器的新后端实际速度未测，不制造精确分辨率时间表。

## 拟定体验门槛（开发目标，未宣布通过）

引用R-02/R-03/R-04与P-01/P-02/P-03/P-04。不降低已有P-02：准备完成区域总体仍以输入到绘制提交P95≤50ms、尽量接近60次/秒更新为目标。先记录同素材30秒短片基线，再构建5/30分钟长片对照，内容、编码、磁盘、质量、内存与动作脚本一致。

| 场景 | 目标和必须同时报告的量 |
| --- | --- |
| RAM命中，前后反复拖动 | P95≤50ms，长片较同条件短片额外延迟≤20ms；有效目标更新至少30次/秒、争取60；单次无更新≤100ms |
| 整片代理已就绪，跨分钟跳转 | 仍争取P95≤50ms；50～100ms登记为与短片有差距，超过100ms不作为同等流畅通过；同时检查最终准确帧 |
| 代理尚未生成的远处 | 单列等待，不混入RAM结果；先低清预览的工程目标≤250ms，达不到明确报告。不能声称所有未准备位置都能像已缓存短片一样即时 |
| 连续拖动与松手 | 最新目标优先，旧任务不排队追赶；拖动允许更低分辨率，松手恢复选定预览质量；不减源帧可访问性、不改圈画坐标与颜色语义 |
| 播放与后台制作并行 | 同时制作情况下至少10分钟连续播放无缓存导致的停顿；记录丢帧、音画差与CPU/GPU/内存/磁盘峰值；不能只测已预热10秒 |
| 资源和恢复 | RAM及现有5GiB总预算守住，暂停/关闭/换片/切模式能取消，重开仅复用完整段，无素材/标注丢失 |

P95不能只统计恰好完成的快速请求：同时报告全部输入数、被替代请求、最长无更新、最终目标等待、画面相对最新输入的落后、掉帧、暖/冷准备状态。绘制提交不等于屏幕物理呈现；真实宿主需独立记录。单次0.88秒相当于50ms的约18倍，只能说明量级落差，不能冒充P95对比通过。

## 自动检查与集中体验顺序

1. 选定一条可接入Eagle的常驻后端，先验证实际原生依赖/渲染通路及准确帧，不并行铺开所有编码。没有通过前，不让用户反复体验小修。
2. 自动记录同动作短/长对照，分别覆盖RAM命中、磁盘代理命中、未生成区、后台制作/关闭重开；低RAM、60fps、VFR、音频长尾、JPEG与代理互切均覆盖。量化不合格由Codex修复复验，不能以合成低清样本推导复杂源通过。
3. 通过自动门槛后，在真实Eagle集中检查宽幅扫动、局部反复搓动、跨分钟跳转、逐帧/标注及后台播放。宿主自动控制不可用时由用户操作观察，技术计量仍由Codex承担。
4. 给出每个场景实际延迟与短片差值，明确未生成区/高规格落差。允许降低预览质量，但不能靠降低更新频率、隐藏等待、削减帧准确性伪造跟手。

本轮没有运行新媒体测试或消耗旧实验预算。后续实现前另立有界媒体现场和资源清单，保持旧证据与冻结发行不变。
