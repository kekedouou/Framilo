# E41 GPU代理拖动超时修复

用户反馈：切换GPU代理后拖动，出现“代理画面解码超时，未显示未经确认的画面”。本地偏好为1080p / NVIDIA代理 / 优先硬件。此前720p独立Chrome成绩不能证明此路径通过。

## 修复前调查与范围

发现明确时序缺口：原生flush（排出待显示帧）在途时，后续请求的8ms排出定时器被跳过；flush完成只清空标记，不再为仍待输出的新请求补排出。该请求可能滞留直至2秒超时并停止会话。这是代码可复现的候选原因，截图本身不能证明所有超时均由此产生。

先增加交错flush/新请求/取消/关闭的确定性回归，再修复排出调度。不增加超时、不绕过帧身份和尺寸验证、不改GPU编码配方，不改用户设置/正式缓存。关联R-02/R-03与P-01/P-02；涉及解码调度，性能验证需要，优先复用已有GPU包进行有界实际解码，不重跑整段媒体生产或历史预算。

本轮仍按E41不提交Git，保留既有未提交工作。实际修复、检查和宿主未验项随后登记。

## 已实施与直接证据

新增scheduleFlush：定时器触发时清空自身句柄；一个flush结束后，为仍在解码阶段、没有排出定时器的请求重新安排8ms检查。保持单次flush在途、最多两个解码槽和2秒原超时。已取消但尚由原生解码占用的帧仍需排出释放，关闭/失败之后不补发定时器。

修复前新增的确定性交错测试失败，明确缺少补发定时器；修复后通过，另覆盖取消第二请求和排出期间关闭，确保位图/原生帧只关闭一次，无残留请求。证据：verification-runs/e41-decoder-fix/regression-before.log、regression-after.log。

复用现有正式缓存中已验证SHA的1080p NVENC包（1,562,285字节），没有重编码原视频、改原设置或清正式缓存。独立Chrome实际解码：硬件优先/软件优先/自动分别两次重建，每次89请求，覆盖首帧、双请求反向读取、8次取消、关闭重开，六组均无超时且关闭后pending为0。末轮事实在native-replay.json，首轮摘要与清理回执在native-replay.log；这是组件解码回放，不是端到端拖动延迟或Eagle验收。

进一步以真实GPU包/原生解码器注入40ms的flush完成回调延迟，制造上述交错：旧代码显示3帧后PROXY_DECODE_TIMEOUT；新代码8帧全部完成、4次串行排出、无残留。native-barrier.json明确标记注入延迟，不用作自然性能成绩。脚本后续运行采用独立时间ID文件，防止覆盖前轮证据。

临时浏览器配置均按annotation-scratch逐文件SHA回执清理；只保留1.56MB包、源摘要、源码快照和有界日志用于复验。未再生产代理，仍在E41剩余有界资源范围内。

当前修复解释并解决了一个可证实时序缺口，**不能据此保证用户Eagle中的所有解码超时都已排除**。真实Eagle108的驱动/硬解表现仍需重新打开插件后集中确认；既有E41图表来自修复前快照，不把本次组件回放当作新优化成绩。
