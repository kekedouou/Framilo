# E41：实测分析与下一步

这轮解决了“等待时没有任何新画面”的明确逻辑缺口。**临时画面约0.18秒出现；准确帧仍约0.9秒，代理生成仍是主要瓶颈，换GPU不等于立刻变快。** 原始数据、条件和边界见[实施报告](report.md)，可视对比见[图表](../../../artifacts/performance/e41-comparison.html)。

## 证据支持的判断

1. 修改前直接跳转/松手会撤销低清，偶发超时累计两次后整段禁用。修复后18次固定冷区跳转都先出现临时图，CPU中位数178ms、P95 214ms；准确帧分别895/1020ms。这是补位改善，不是准确解码快了五倍。
2. 快拖只允许“完全等于最新请求”会丢掉大部分正在返回的临时图。改为有界近邻追随后，约0.8秒轨迹有13～14张图，最终松手只认可准确目标；低清不能用于永久标注。远跳严格淘汰旧帧，不能用近邻优化掩盖错位。
3. 已准备代理磁盘P95约49ms、热RAM约7ms，明显小于冷区约1秒。主要等待在画面供应前，不能简单归因为最后的Canvas绘制。
4. FFmpeg首源帧、首包和整段发布是重叠管线上的里程碑。它们显示每次重新启动/从关键帧前滚，再等待整段发布的固定成本仍在，不能把这些时间相加或全叫编码。当前GPU高质量配方还生成约2.6倍字节，读写与校验也要处理更大包；三轮未证明端到端稳定加速。
5. 记录错误与软件慢不是一回事。被截断/路线不全的证据不能进报告；完整测试中真实测到的慢请求、按协议超时和错误必须保留，不能只留好成绩。

## 已采取的取舍

保持CPU H.264默认和JPEG已认可策略；GPU H.264为可选。播放解码有硬件偏好设置，但Chromium未提供实际后端证明时不写“已硬解”。GPU同码率探测仅说明可进一步控制体积，目前没有把一帧PSNR当作整片观感验收而更换正式配方。

本轮没有引入整片必须等待的额外低清任务，没有降低正式画质、删动效或增大RAM/磁盘上限。5GiB正式磁盘额度仍可能限制全片代理覆盖，不等于保证所有长片都准备完。

## 后续优先级与验收建议

| 优先级 | 方向 | 应验证什么 |
| --- | --- | --- |
| 1 | 前台目标帧优先出图，再补完整段 | 原子发布与源PTS不放松；冷区准确帧P95再降，不靠临时图代替；取消/快拖/反向跳转不积压 |
| 2 | 复用生成端解码/编码，减少短段启停 | 保留前台可抢占和有界后台；证明初始化成本下降且关闭/模式切换不会挂起 |
| 3 | GPU码率与体积配方 | 同素材多帧发光边缘/纹理/颜色，与CPU相近体积下比较端到端，不只看编码fps或单帧误差 |
| 4 | 原片低清路径仍慢时，逐步稀疏预览 | 不增首播门槛，明确临时帧时间误差、缓存上限和生产竞争；GPU/CPU同时繁忙时仍跟手 |

上表是后续方向，不冒充已实施。当前必要人工体验集中于Eagle：冷区快拖与松手、再次拖动是否回跳、CPU/GPU切换、监测窗口菜单和关闭闪屏。若真实宿主仍明显差于独立浏览器，应先记录同路径等待，不继续用本地成绩宣布通过。

## 复盘

可复用：先分RAM、已准备磁盘和冷区，用同素材同路线计量，低清与准确帧分别统计；错误状态和发布事务用故障注入检查。曾经的错误：只在拖动中请求低清、两次超时永久关闭；严格最新请求过滤反而使快拖缺图。修正：最终跳转继续补位、超时恢复、有界跟随且准确帧严格代次保护。独立媒体检查不能再当作Eagle原生界面验收。
