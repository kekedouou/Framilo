# 这次等待问题的结论

不能把所有问题都归为代理生成慢。现有记录证明：**代理未完成时，等待目标资源是主要瓶颈；代理完成后，最新体验记录里的已完成操作很快。** 资源等待里编码、排队、校验各占多少，旧记录没有拆开。

下表时间为原记录UTC（北京时间加8小时）。

| 记录 | 实际发生的情况 | 结论 |
| --- | --- | --- |
| 07:11 标准测试，96秒AV1原片、1080p代理 | 最慢成功请求6384.9ms，资源返回6382.1ms，解码1.9ms；后来请求超过剩余测试时限 | 当时主要卡在资源供应，不能解释成解码慢；并非每次都等满8秒，单请求/场景/整轮剩余期限取最短 |
| 08:52～08:56 三次标准测试 | 代理未就绪，零正式请求 | 不是测试中播放器崩溃；原入口把前提不满足保存为失败，造成混乱 |
| 08:57 标准测试 | 完成预热后，等待缓存连续稳定300ms；10秒内未稳定，零正式计时请求 | 用户允许10GiB缓存且提前解压开启；代码仍会持续填充。计时起点要求与后台策略冲突，缺少当次逐项队列证据，不能推断其它线程出错 |

“未细分”的一大部分来自漏记：1103次输入时已命中RAM的操作无需解码，但仍需经过界面处理及等待绘制。旧逻辑把它们全部放入“未细分”。这些操作合计6230.6ms，占旧“未细分”合计8003.5ms的约77.9%。这是**请求耗时加总**，不是用户连续等了6秒。新记录另测任务槽排队、复用解码、分段租约、读取、原生解码、位图转换、字节复制与Canvas提交；旧数据缺失不补造。

## 代理速度与什么有关

| 因素 | 本项目的对应情况 | 可考虑的优化方向 |
| --- | --- | --- |
| 原片编码、尺寸、帧率 | 这些记录是AV1；需先解码原片。4K60比1080p30要处理的像素量大得多，但总耗时不是简单倍数 | 核实当前硬件/FFmpeg支持后，对原片解码与缩放做硬件加速对照 |
| 代理画质和编码器 | 当前libx264、ultrafast、CRF20、全IDR；CPU编码。播放的prefer-hardware不是代理生成使用GPU的证据 | 尝试NVENC等硬件编码，并验证块状伪影、色彩、磁盘大小；不能只追速度 |
| 任务切分 | 最多约2秒或120帧一段，分段启动FFmpeg；跳转会改变优先目标 | 降低反复初始化与重复读取/解码成本，评估较持久的生成进程，保留取消和目标优先 |
| 调度与校验 | 等分段租约可能含其它任务、生成、身份检查；旧计时不能拆开 | 先用新计时分辨排队/供应与读取，再决定改哪里；不删除数据保护检查 |
| 磁盘和CPU/GPU竞争 | 原片/缓存读写、生成、播放和缩略图并行 | 根据实测限制后台竞争。增加RAM不能自动加速未生成帧的编码 |

建议顺序：先确认新记录的目标供应/队列占比，再比较“减少重复初始化”与“原片解码→缩放→代理编码全链路硬件加速”。仅打开一个硬解选项不保证更快，CPU/GPU往返复制也有成本。降低画质会影响体验，仍需用户选择；本轮未改编码、画质或正常缓存策略。

依据：[NVIDIA FFmpeg指南](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/ffmpeg-with-nvidia-gpu/index.html)说明硬解、缩放、硬编及小段转码初始化开销；[FFmpeg文档](https://www.ffmpeg.org/ffmpeg.html)说明硬件加速与GPU/系统内存复制成本。这里只引用原理，不拿公开示例速度当作本机实测。
