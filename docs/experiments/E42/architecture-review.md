# E42 后续架构复核与下一步建议

2026-10-28。用户要求继续分析记录、复核分段代理与竞品源码、规划方向。本轮只读播放器和已有计量、查阅公开源码；没有生成媒体、变更播放行为、换编码配方或接受基准。此文是建议，不是新架构已通过或已接入。关联 R-02/R-03/R-08、P-01～P-04。

## 结论

需要调整供帧架构。保留分段作为磁盘存储单位，但不要把“完成一个代理段”作为交互出图的必经条件。当前主要矛盾是每段独立生产、整段发布屏障、原片临时预览成本和频繁重定向相互叠加。GPU编码器是否最快，不能从这条端到端链路直接判断。

建议三个职责分开：交互预览直接给图；准确帧按源PTS确认；全片代理持续后台生产。预览不能排在整段转码后面，后台也不能因鼠标不断移动而永远做不完。

## 当前实现的具体问题

1. **生产和存储粒度绑定。** long-media.cjs 的每段不超过120帧/2秒，decode 每次启动 FFmpeg；segment 只有在视频、音频、进程结束、PTS核验及事务完成后返回。段内首图已经生成也不能直接给前台。音频和安全检查本身不能取消，应把可验证的临时交付与完整持久发布分开。
2. **低清目前只是小尺寸显示。** quick-preview.js 的 video.src 仍为原片，先原片寻帧解码、再绘制成最多480×270画面；64张小图是用过才缓存，不是全片轻量代理。原片4K长帧组的解码依赖不会因画布缩小而消失。80/180ms重定向、超时退避及新旧结果筛选可能使快拖不断重启有用工作，具体比例尚未计量。
3. **全片后台逻辑存在，但进度无保证。** proxy-background.select 顺序是当前位置及邻近段、标注帧/段、cursor遍历剩余全片。task-worker 只在没有前台控制任务时安排后台；跳到不同未就绪段会中止当前后台，尚未提交部分不能复用。频繁拖动会使全片补齐长期让路。达到磁盘上限前128MiB余量会进入 budget，错误会进入 error，均不能称完成。用户看到“只准备当前位置”与该机制吻合，但无新现场记录，不能断言某次一定是饥饿或容量停止。
4. **GPU模式不代表所有源都全链路硬件处理。** proxy-encoding.cjs 只有支持的编码、8位420、BT.709、无旋转和方形像素等条件才走CUDA解码/缩放；否则仍可CPU解码缩放加NVENC编码。已有固定4K样本的记录明确为CUDA解码、CUDA缩放和NVENC，不是忘开硬解。

## GPU慢的归因边界

对旧诊断中源SHA匹配、1280×720、h264_nvenc 的40份清单重新计算最近秩中位数：启动至首源帧1049ms；逐条计算“首编码包减首源帧”后中位数45ms；“processAndPublishMs减首编码包”中位数875ms。各段内容/长度不同，部分清单早于体验录制，不是新的固定性能成绩；这些异步流水线里程碑不能相加当总耗时，也不能称45ms就是纯NVENC编码。

E42无播放器/缓存/音频的独立视频试探，首编码包仍需1322～1398ms、完整120帧约1952～2026ms。因此界面和音频不是秒级等待存在的必要条件；生产端本身确实慢。

已证实的结构性代价：反复启动FFmpeg与硬件上下文、重复源寻帧及前滚、等段完成再发布。额外因素是CPU CRF20与GPU QP20不等质量/等码率；此前固定样本GPU体积约CPU的2.6倍，增大写入/校验成本，不能推广成所有视频倍率。兼容CUDA路径没有CPU逐帧下载再上传缩放，不能臆造“每帧来回搬运”是其根因。

**还没有唯一的“终极硬件原因”证据。** 首源帧之前的1秒尚未分别量出进程、驱动初始化、容器探测、源解码前滚占比；原片预览与转码争用、驱动队列及主线程长任务仍需分开验证。NVIDIA官方明确指出小块独立FFmpeg转码会被初始化拖累，建议减少进程并共享上下文；这是支持实验方向的资料，不是本机毫秒归因证明。[官方指南第7节](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/ffmpeg-with-nvidia-gpu/index.html#performance-evaluation-and-optimization)

## 下一步顺序与技术关

### 1. 先让交互出图脱离代理生产

隔离原型对比：现有原生video回退、可控常驻源帧读取、已准备的独立轻量预览。常驻源帧读取应保留解封装/解码状态、复用邻近结果、优先最新有效意图，把解码后目标帧直接返回，不再编码写盘后重新解码。现有video已经是常驻对象，问题不只是少建一个对象；需要可控制前滚、取消、帧身份和提交时机。实现可控原生读者可能需要新的原生组件/构建依赖，须先明确维护与打包代价，不能把普通FFmpeg CLI称作任意可寻址服务。

快拖按处理能力和拖动速度选取有价值的画面，近处密、远处疏；限制显示的时间偏差，松手与逐帧回到准确源帧。取消排队废任务，已开始任务是否重定向依据方向/距离/完成进度决定，避免固定80ms反复重来。临时图不用于标注或记录缩略图。

### 2. 真正轻量的预览层，与整片持续生产协调

候选是逐步生成较低分辨率、稀疏时间采样且容易随机读取的预览；先扩大覆盖，再加密当前位置。具体尺寸/采样率与预算是待选参数，不改正式画质。这能让已覆盖远处立即有图，但**第一次打开、尚未准备的位置仍有物理读取/解码成本**；低分辨率输出不免除原片参考帧解码。不得宣传无等待覆盖整片，或把重复旧图计为流畅新图。

全帧代理继续自动补全：连续解码/编码，分段落盘发布，已经完成的片段可用；连续生产不等于生成完整片才能用。前台和后台有独立职责及总资源上限；交互繁忙时降后台速率或在安全检查点暂停，保留上下文/进度，空闲继续补齐全片。不能用增加无限并发换速度，也不能在缓存不足时假报完成。须验证持续拖动之后可恢复补齐、错误/容量状态明确。

### 3. 再决定GPU路径和编码配方

同源对照短进程/连续生产、CPU解码+CPU编码/CPU解码+GPU编码/兼容GPU全链路，分别测首图和整片吞吐。先保持现有配方测试架构效果；再做相近画质或相近体积的配方比较，不能把CRF20=QP20作为公平前提。H.264/HEVC/ProRes等取舍另列画质、磁盘、首图及兼容代价，不在此轮擅自更换默认。

## 验证和停止盲调条件

下一实施阶段需要性能验证：触及寻帧、调度、代理、缓存与传输。继续用固定源、固定轨迹、冷/磁盘/热RAM分组、CPU/GPU分别记；真实Eagle和独立Chrome分开。新增快速反向拖动、后台运行/暂停对照、原片预览竞争对照、等待期间反复重定向及静置全片补齐。

沿用E42低清首图P95≤200ms、准确帧P95至少减半的未达目标；另建议对已覆盖轻量预览追求P95≤50ms、快拖新画面空档≤100ms。这是更严格的候选体验门槛，非已通过标准。记录响应、画面新鲜度/目标时间偏差、新图频率、松手准确帧、错误/取消/队列占槽、资源峰值、全片完成时间；不只报成功请求P95。

先过源PTS/可变帧率、反向、取消、关闭重开、旧缓存兼容与有界占用关，再接正式。如果常驻直接取帧仍无法将冷区首图压进200ms，就明确列出原片解码代价和轻量预览预热时间，不能继续承诺所有第一次远跳近乎零延迟。若必须新增原生后端才能通过，应交代依赖/安装包/维护成本并做架构取舍，不继续把主力投入微调超时。
