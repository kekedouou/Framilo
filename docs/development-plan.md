# 开发与维护流程

本页管理执行流程、文档职责、Git与文件整理；当前任务/授权/待验只见[当前交接](progress.md)，未来优先级见[路线图](roadmap.md)。

## 开发单元与完成条件
一个单元是可独立说明目的、检查和恢复的改动，可为功能、修复或纯文档整理；不按消息、按钮或编辑次数划分。大阶段可分多个单元，用户验收按功能包集中组织。
开始先核对授权、R/P、影响文件/模块、测试副作用/目录/预算及既有工作区归属。多阶段计划在编码前登记；计划写目标/假设/边界/验收，报告写结果/失败/证据/限制，不用计划代替成绩。
获批范围内连续实现、检查、修复；必要人工、重大取舍/新受限操作/关键技术关才暂停依赖部分，其余继续。完成代码、本地模拟、真实Eagle和人工观察分开，未验不得冒充通过。
收尾先保存证据/文档、按范围整理、运行适用检查、审查差异再提交；有待验宿主可提交候选，须明确状态，不宣告发布或下一阶段获批。

## 文档维护机制
这是每次收到“写入原则/要求”时由Codex执行的流程，不是后台自动改写程序：
1. 先定位本主题的主文档及原条款，核对当前明确决定与已有授权。
2. 相同要求合并去重；补充原位更新；替代要求更新现行条款，并在阶段/维护记录保留旧决定和原因。只有新的通用工程规则进入AGENTS；功能参数放产品/专项，验证动作放验证规范。
3. 保持一项事实一个维护位置，其他文档链接过去。现状只在progress维护；README/地图不复制状态段。按主题组织，不把新日期/阶段当作追加章节。
4. 检查下表受影响正文、导航、所有引用与旧记录兼容；不受影响/冻结文件注明理由，不伪改日期。历史仅为追溯，不把其权限/命令当现行授权。
5. 运行check-docs和check-handoff，审查语义冲突、被替代条款和遗漏的读写端；脚本只检已编码的结构/状态/链接，不能替代人工语义核对。记录改了哪里、为何归类及验证结果。

| 文档 | 唯一职责 | 何时更新 |
| --- | --- | --- |
| AGENTS | 通用权限、实施与完成底线 | 新通用要求或原规则改变 |
| project-profile | 身份、目录、按任务导航、命令副作用 | 路径/入口/模块导航改变 |
| progress | 唯一当前阶段、候选、授权/结果/待验、工作区例外 | 当前交接变化；旧过程归档 |
| product | 按功能的已批准行为及R/P | 产品/交互/资源语义改变 |
| architecture | 当前模块、运行链与数据/进程边界 | 技术职责/格式/运行链改变 |
| development-plan | 工作流程、文档维护、Git与F规则 | 流程/交付规则改变 |
| verification | 按影响选择检查与通过条件 | 验证契约、读写/计时/安全场景改变 |
| roadmap | 未来方向、优先级、待决事项 | 需求/证据影响路线 |
| 实验plan/report | 单阶段计划与真实结果 | 该阶段实施/验证；旧成绩冻结 |
| releases及能力表 | 已发包来源、恢复；当前能力参数 | 发布或能力契约改变，不覆盖冻结包 |
| history与历史progress | 原条款/旧过程 | 只归档或修复导航，不改验收结果 |

历史正文迁移时保留来源提交、前后摘要、路径映射与可恢复内容；只修改相对链接/历史说明。新增阶段更新[实验索引](experiments/README.md)，不把全量历史塞回入口。默认必读三文件合计≤10000字符；超限先整理归档，不能单纯挤行或提高限额。

## Git提交边界
- 调查/问答无修改不提交；同一单元的连续修改不逐消息/逐编辑提交。单元完成且相关检查/记录齐备，Codex主动提交本地Git，不等待提醒；大任务可在可独立核验/恢复的节点分次提交。
- 提交不等于宿主验收、发布或进入新范围；未完人工/宿主验收写明候选及待验。测试失败不伪装完成；确需保存失败诊断节点必须明确状态和后续恢复入口。
- 开始记录基线和其他任务差异；只暂存本单元精确文件，核对内容及暂存清单，不使用全量暂存混入旧工作。文件若混有其它任务编辑，只暂存自己的块或先保全隔离。
- 提交前：相关检查、node scripts/check-handoff.cjs --base HEAD，以及git diff --check。存在非本单元代码时可另传--scope-file指定已核对的项目内路径清单；脚本仍列出未纳入路径，不将其当本轮修改。
- 使用路径限定提交或隔离索引，保护原有暂存内容；不改写历史、不回滚他人工作、不自动推送。积累工作如实补录，不伪造历史节点。
- 提交后执行node scripts/check-handoff.cjs --require-clean；其它任务仍有差异时登记路径/归属/原因，按失败如实报告，不混入、不丢弃、不声称干净。最终给出短号、适用验证和未验事项。
- “暂不提交”例外必须写适用任务/文件、原因、结束条件；历史例外只约束当时范围。本轮结束后不得用旧例外覆盖新的默认提交规则。

## 文件整理F-01～F-07
| 编号 | 必须遵守的规则 |
| --- | --- |
| F-01 归属与路径 | 先有候选清单及有界记录空间；核对真实绝对路径、任务、目录边界、文件身份/内容及占用。不跟随链接，不清未知/越界目标；Git忽略不等于删除许可。 |
| F-02 临时/未完成 | 等进程、流、不可取消任务真实停止后清本任务无用产物；强退恢复核对出生/后代和独占保护，不能只凭PID消失或年龄删锁。 |
| F-03 完整缓存 | 按内容/处理版本复用，容量不足淘汰可确认归属且未占用的旧缓存；当前源/活动/验证所需保护，无法安全腾位明确失败，不借恢复清空有效缓存。 |
| F-04 重复保存 | 完全相同素材/代码/协议/轮次/截止点/测量/反馈且已有记录有效才复用；新操作/测量/变化快照保留，不合并协议要求的多轮。 |
| F-05 证据 | 保留验收引用/关键失败原件及变化测量；仅清已核对原件/诊断保全的严格重复副本、可重建无用媒体，不凭相似度删证据。 |
| F-06 容量与回执 | 盘点预检、预留记录、复核、定点删除、记录释放量/跳过原因；满额停止不擅增额或删证据腾位，变化停止该项。各实验配额独立；T0缓存1GiB/证据128MiB及原T2/T4配额不扩大；现行代理/JPEG额度见产品。 |
| F-07 项目/交付 | 保护源码/Git、本机配置、唯一输入、素材/标注及封存原型；已替代构建/下载中间件/临时文件按用途、重建来源、占用与引用清理，不按年龄清。存疑先说明影响再交用户决定。 |

日常临时文件任务结束即整理，阶段收尾盘点旧副本，不拖到发行才清。不新增后台清理框架；正常产品缓存维护与开发输出整理分开。
dist只作构建/验收暂存；日常安装迁仓库外非C盘，仍注册运行目录先保护。远程附件大小/摘要/实际下载核对且可恢复后只留最新发行ZIP/校验；唯一待发包和必要证据列保留理由、移交条件、清理触发点。
移交使用同版本干净运行文件/必要偏好，不搬归属旧根的cache；新位置宿主加载确认前不删旧入口。清理同步下载说明/复现命令；已清验收目录不能假称verify-install仍能直接执行，冻结包不为文档更新重建覆盖。
发行本机回执仍沿verification-runs/release-0.1.0-beta.2，总1MiB、单份128KiB、最多16文件，不挤占旧实验配额；Git不能恢复忽略的二进制/缓存，必须说明恢复来源和成本。
原完整F机制与历史数值见[原整理条款](history/2026-10-31/development-plan.md#t2-文件自动管理计划f-01f-07执行中)。

## 特殊故障与历史边界
Codex变更入口异常先核对真实Git根/状态/提交，再核对项目绑定；不删/重建.git，不直接改应用数据库。工具不可用就列剩余人工步骤，不宣称界面修复。
原型A/B/S1、旧T0～T4、强退/标注写入、历史reset和媒体命令只按具体授权/预算执行，不因文档整理重跑或恢复已消费授权。历史任务入口见[归档计划](history/2026-10-31/development-plan.md)与[阶段索引](experiments/README.md)。
